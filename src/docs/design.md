## 一、概述
日常工作分散在多个飞书群聊、私聊中（需求沟通、问题排查、评审、协作），信息碎片化；每周每月手动回忆整理周报/月报，耗时且容易遗漏。

**本工具解决的核心问题**：把「回忆 + 手写工作总结」变成「每天花 1 分钟点几下确认，月底一键成文」。

- 自动抓取我在飞书的发言（含别人布置给我、点名要我做的事）
- 大模型把围绕同一件事的碎消息**凝练合并成一张工作卡片**
- 用户逐卡确认 / 忽略 / 编辑，确认的进入历史归档
- 按周 / 月一键生成正式报告（业绩维度 + 文化维度），可直接排版、富文本复制
**演进**：v0.1 单人本地验证 → v0.2 初步方案设计 → v0.3 多用户版上线（OAuth 登录、数据按人隔离）→ v0.4 抓取来源扩展（@我 / 单聊 / 小群）+ 跨来源自动合并 + 报告流式生成与富文本编辑 → v0.5 产出形态扩展（实习总结 / 简历条目、工作画像、报告三种文体）+ 归档一键去重 + 空正文兜底与降级归因 → v0.6 抓取来源再扩（含我写的文档）+ 反馈墙可回复 → v0.7 报告对话改稿（全文重写 + 逐行 diff 预览 + 采用才写回）→ v0.8 稳定性与引导（前端样式改本地内联、排错提示配直达按钮）→ v0.9 待确认卡片一键全确认 → v0.10 站内通知（铃铛）+ 问题反馈状态可改→ v0.11 需求状态可改（待处理 / 处理中 / 已上线）+ 状态变化也提醒。

## 二、用户与账号体系
- **多用户**：每位用户用各自飞书身份登录（OAuth 粘贴授权码），数据按 `open_id` 严格隔离——每人只能看到、抓取、汇总自己的消息。
- **会话**：登录后 30 天免重登；过期重新授权即可。
- **大模型**：每人填自己的 Key / Base URL / 模型（打码存储，只改模型时无需重填）。
- **机主管理**：部署更新页面、删除全站反馈、改反馈状态仅机主可操作（管理员会话）。

## 三、核心流程
```
① 抓取  ──>  ② 凝练合并  ──>  ③ 确认/忽略  ──>  ④ 沉淀归档  ──>  ⑤ 一键成文
```

### ① 抓取（手动触发，走 SSE 进度）
- **范围**：当天 / 前一天 / 日期范围（单次 ≤ 31 天，可勾「仅工作日」）。
- **来源（五路）**：
    1. **群聊里我发的消息**（含回复别人）—— 默认路径；
    2. **单聊**布置给我的任务（勾选，默认关，模型识别）；
    3. **3~4 人小群**布置给我的任务（勾选，默认关，模型识别）；
    4. **大群里别人 @我、需要我去做的事**（勾选，默认关，模型识别；典型场景：对方 @我 让我处理某事、我做了没回复——以前会整条漏掉）；
    5. **我写的云文档 / 知识库文档**（勾选「含我写的文档」，默认关）—— 设计方案、调研、复盘这类活儿常常从没在群里提过；个人云文档与知识库都搜，**只看我名下、最后一次由我编辑的**，会议自动生成的妙记不算。飞书搜索按相关性返回，多关键词并集也不保证覆盖全部，**没抓到的手动补卡**即可。
- **@我的判定**：消息 `mentions` 里点名我的 `open_id`；`@所有人` 的广播 id 不以 `ou_` 开头，天然不会命中，不算任务。
- **上下文窗口**：@我 的消息带同群此前的连续发言（≤4 条 / 5 分钟窗口）一起给模型，否则"@张三 看下这个"无从判断要做什么。
- **取消**：进度条旁「✕ 取消」——协作式取消，已抓到的卡片保留，没抓的部分停止。
- **进度**：8→90 扫描会话（含"已找到我的消息 N 条、别人@我 M 条"）→ 97 扫描单聊 → 98 识别小群/@我 任务 → 99 合并 → 100 完成（带"已合并重复 K 张 / 清理旧卡 / 跳过已忽略"汇总）。
### ② 凝练合并
- **凝练**：每路来源由大模型把一组相关发言重写成**一句话工作卡片** `{title, detail, project, source_count}`。
- **合并（跨来源去重）**：合并动作**只在大模型做分组**（输出下标组），由代码**确定性地**合并——标题取组内消息最多的那张、详情去重拼接、项目取非占位的那个。模型的错误最多表现为"没合并"，绝不会表现为"丢卡"。
- **幂等重抓**：同一天重抓时，标题会**锚定上一轮**的 pending 标题（模型改写措辞不改变卡片身份），重抓结果稳定可复现；重抓前清掉当天旧「待确认」卡，已确认 / 已忽略的不受影响。
- **忽略记忆**：忽略过的卡片以其 `(日期, 项目, 标题)` 指纹记忆；标题被模型改写后仍用「同项目 + 语义相似 + 共享专有名词」模糊兜底识别，**不复活**。
### ③ 确认 / 忽略 / 编辑
逐卡操作：**✅ 确认**（进归档，是报告的素材）／ **🗑 忽略**（记住，以后不再出现）／ **✏️ 编辑**（改标题/详情/项目）／ 删除（可恢复忽略记忆，用于误忽略自救）／ 手动新增。待确认卡多时用 **✅ 全部确认**：一次确认**当前列出的**那一批（「只看当天」就只认当天，「全部待确认」才是全部）。没有批量接口，服务端逐个复用单张确认那套调用、**顺序发不并发** —— 一次几十个并发请求会把服务打满。

### ④ 沉淀归档
- 已确认卡片按**月份网格 → 下钻按日分组**；支持关键词搜索、按月 / 按日就地补录、就地编辑、删除（可同时解除忽略记忆）。
- **一键去重（月视图）**：把同一天里重复记录的卡片自动成组，**先预览、逐组可取消、确认后才写库**。判重两层：先本地文本相似（不依赖 Key 也能用），再大模型语义分组，两层结果用并查集合并。
- **只在同一天内合并**：跨天合并会让某一天整天没有记录 —— 周报按日期组织会缺块、工作画像的「覆盖天数」会虚低。宁可漏合，不跨天。
- 合并在**单个事务**里完成（更新留存行 + 删除被合并行 + 按新的「日期 + 项目 + 标题」重算 sig）。归档是已确认数据，**没有「重抓重建」的退路**，绝不能留下「原卡已删、留存卡没更新」的半截状态。
- 服务端**不信任前端传来的分组**：逐组校验「全部属于本人 / 全部 confirmed / work_date 完全相同」，任一不满足就整组跳过。
### ⑤ 一键成文（报告生成）
- 周报 / 月报 + 快捷范围（本周 / 本月 / 上一自然月 / 考勤周期 25→次月24）。
- **三种文体**（同一批条目，只改写法）：**叙述式**（连贯成段，正式提交用）／ **提纲式**（小标题分层，会上过一遍用）／ **要点式**（短句罗列，自留档 / 组内同步）。每种都可「看样例」，样例只是骨架示意、不含任何真实工作内容。
- **实习总结 → 简历条目**：另一条产出线，范围是「入职日期 ~ 今天」（入职日期存浏览器）。两步各自独立成文、互不覆盖：① 五段式实习总结（实习概览 / 主要工作与产出 / 能力与方法沉淀 / 收获与不足 / 后续规划，按月梳理成长脉络）；② 3~5 条简历条目（动词开头，「做了什么 + 怎么做 + 结果」）。**量化数字只取自工作条目，模型不替用户编。**
- **流式生成**：POST 任务后走与抓取同一 SSE 通道，阶段进度（读取条目→分组→凝练）+ 正文**逐字实时上屏**。
- **输出结构**：【业绩维度】总述 + 主要工作内容（按项目分组）+ 问题与反思 + 收获与成长；【文化维度】对照公司两大价值观（以客户为中心的价值洞察力 / 低成本短周期检验）。文字格式约定：小节加粗、条目数字编号（不带 `#`/`-`/`*`，便于直接使用）。
- **富文本编辑与复制**：报告渲染成可编辑富文本（加粗 / 下划线 / 编号 / 项目符号工具栏），复制时携带 HTML+纯文本，**粘进飞书文档 / Word 加粗、下划线、编号原样保留**。
- **四层回退链**（详见「六、关键设计决策」第 5 条）：流式 → 检出空正文 → **加大额度**的一次性重试 → 本地按项目罗列。**只有真的落到最后一层才算降级**，中间换路只是提示。
- **降级必须说清为什么**：降级原因（未配 Key / 异常类型 / 网关回的 finish_reason 与 completion_tokens）随 SSE 的 completed 事件回传，前端黄条直接照念，同时写进正文 —— 进度通道的提示会被后一条盖掉，用户根本看不到。
- **复制并去绩效**：用**同步**的 execCommand('copy') 复制富文本之后再开绩效标签页（异步 clipboard API 会因为失去用户手势而被浏览器拒绝）。绩效自评没有「写入自评正文」的开放接口，所以只能做到「复制好 + 送到门口」，最后一下 Ctrl+V 由用户自己按。
- **💬 对话改稿**：报告生成后可以用大白话提修改要求（「第二段那个平台名写错了」「问题与反思太虚，结合第 3 条具体点」），大模型据此**重写全文** → 前端算**逐行 diff 预览** → 点「采用」才写回编辑器，另有单级**撤销**。
- **改稿失败绝不产出文本**（与生成路径相反的取舍）：生成失败会退回本地罗列（「总要给用户一篇」），改稿不能 —— 用户手上已经有一篇好稿，退回罗列稿等于把它毁掉。所以失败只提示、编辑器一个字不动。
- **素材按生成时的范围快照取**：改稿用的是生成那一刻的日期范围，不跟当前日期框走 —— 免得用户生成完改了日期，模型拿新范围去核对旧报告、把对的地方改错。

## 四、功能模块
- **✅ 每日工作确认**（核心页）：日期切换、抓取入口 + 取消、进度条、待确认卡片逐卡确认/忽略/编辑、**一键全部确认**、手动新增；抓完自动切到所抓日期。
- **🗂️ 历史归档**：已确认工作沉淀库；关键词搜索、月份网格 → 下钻按日分组；条目可补录 / 就地编辑 / 删除（可解除忽略记忆）；月视图提供 **🧹 一键去重**（同日重复合并，先预览后写库）。
- **📄 报告生成**：见上文；支持编辑后复制；生成后还能 **💬 对话改稿**。
- **🎓 实习总结 → 简历条目**：入职至今的全部已确认条目 → 五段式长文；再凝练成可直接写进简历的 3~5 条。两块结果各存各的、互不覆盖。
- **📊 我的工作画像**：总条目 / 覆盖天数 / 项目数 / 日均产出，加投入 Top5、按月分布、最高产月份与最忙一天；**纯前端计算，只看自己的已确认条目**，不上传、看不到别人。
- **🎯 绩效自评**：首页快捷入口，新标签页直达绩效主页；报告页配套「🎯 复制并去绩效」。只是入口，不读也不写绩效数据。
- **🕹️ 像素小鸟**：摸鱼小游戏 + 服务端排行榜（每人最高分）。上榜身份可选「我的账号 / 匿名 / 自定义名字」，每个身份各记各的分。
- **🎁 最近上新**：更新日志硬编码在前端，进站弹一次、叉掉即写入已读版本号（localStorage 独立 key，不进 ws_settings，免得被「恢复默认」连带清掉）；版本号变了才会再弹，首页常驻横条随时回看。
- **💴 来财**：月薪/日薪（÷21.75 折算）、计薪模式（工作时段 09:00–18:00 可改 / 全天）、每秒实时跳动当日进账；纯前端。
- **🤖 大模型设置**：每人自己的 Key / Base URL / 模型。
- **全站统计**：累计浏览、累计抓取触发。
- **反馈墙**：新功能需求 / 问题反馈，可点赞排序，**可回复讨论**（本人可删自己的回复，机主可删任何一条），机主可删卡片、可改每条的状态 —— 需求是「待处理 / 处理中 / 已上线」，问题反馈是「待处理 / 处理中 / 已修复」，提的人一眼能看出自己那条走到哪了。
- **🔔 站内通知**：有人回复了**我提的 / 我回复过的**话题，或那几条的**状态被改了**，顶部铃铛亮红点并给出条数；点一下跳到那几条并记为已读（已读标记按人存在浏览器 localStorage，不落库）。**别人之间的对话、别人的帖子被改状态，都不会打扰我。**
- **个性化**：主题色、标语（含轮换）、入场动画。
- **机主管理**：网页自助部署（白名单文件上传 → 语法校验 → 自动备份 → 自动重启）。

## 五、技术架构
**设计原则**：单文件前端（Tailwind 本地预编译后内联，零运行时构建）+ 单入口 FastAPI + 内存任务 + SSE 进度，一路沿用被验证过的轻量套路；新增能力均为增量模块，不在旧逻辑里打孔。

```
浏览器（单文件 SPA：backend/static/index.html）
  Tailwind CSS（本地预编译、内联进 index.html）+ Alpine.js（CDN）
  currentTool 控制「工具箱首页 + 单工具全屏页」
        │  fetch('/api/xxx/submit') → task_id
        │  EventSource('/api/task/{id}/stream') → 阶段进度 + 内容实时上屏
        ▼
后端（FastAPI，backend/main.py 单入口）
  · 认证：/api/auth/feishu/start · /api/auth/feishu/exchange · /api/auth/logout · /api/me
  · 抓取：/api/crawl/submit · /api/crawl/{task_id}/cancel
  · 条目：/api/workitems（GET/POST）· /api/workitems/confirm · /api/workitems/{id}（DEL）
  · 报告：/api/report/generate（POST → 流式 SSE）
  · 其他：/api/settings(/llm) · /api/stats · /api/feedback · /api/bugreport · /api/admin/deploy
  · 共用进度通道：/api/task/{task_id}/stream
        │  submit 后 BackgroundTasks 起 _process_*，异步队列承接 SSE
        ▼
服务层（backend/services/）
  · feishu_chat_service  抓取群聊/单聊/@我 消息（谓 feishu-sync）+ 上下文窗口组装
  · llm_service          统一封装公司大模型网关（OpenAI 兼容）；_chat + _chat_stream
  · aggregate_service    本地启发式凝练兜底 + 卡片过滤/相似度判定（忽略记忆、标题锚定）
  · report_service       报告提示词 + 清洗 + 流式/兜底
  · db                   唯一持久层（SQLite 库）
        ▼
外部依赖
  · 飞书 OpenAPI（经 feishu-sync 包：list_chats / list_messages / 文档编辑）
  · 公司大模型网关（/v1/chat/completions，支持 stream）
```

- **v0.5 新增端点**：归档去重 /api/archive/dedup/scan（SSE 任务）· /api/archive/dedup/apply（同步写库）；小鸟榜单 /api/game/leaderboard · /api/game/score。去重扫描**完全复用抓取那套 SSE 基建**，没有新增事件类型。
**v0.6 / v0.7 新增端点**：反馈回复 /api/feedback/{fid}/reply（POST / DELETE，fid 全局唯一、两个 tab 共用）；**对话改稿 /api/report/revise（POST → 复用同一 SSE 通道）**。抓取来源扩展走既有 /api/crawl/submit（只加勾选项）。三者都**没有新增 SSE 事件类型** —— 改稿收尾仍用既有的 completed / error。
- **v0.8 ~ v0.11 新增端点**：反馈状态 **/api/feedback/{fid}/status（POST，仅机主）** —— 档位按 kind 分（见 db.FEEDBACK_STATUSES），路由按 db 层的返回码区分 400（值不在该 kind 的档位里）与 404（条目不存在）。站内通知**没有新端点** —— 前端在既有的 /api/feedback + /api/bugreport 返回体上算未读，已读标记只存浏览器。

### 任务与并发
- 抓取 / 报告都是「submit → asyncio.Queue → `asyncio.to_thread(流水线, on_progress)` → SSE」：线程里产生的进度用 `loop.call_soon_threadsafe` 投递，杜绝跨线程直接写队列。
- 任务是内存态（重启即丢，个人工具可接受）；已抓数据 / 卡片已在 SQLite 持久化。
- 数据库单连接 + 锁，多用户低并发足够。

## 六、关键设计决策
1. **模型只做分组、代码做合并**：卡片身份（标题）必须确定可复现——这是「重抓幂等」和「忽略记忆」的地基。模型输出不存在时，一切以标题哈希为键的记忆机制都会失效；合并的"事实"（标题/详情）由代码从输入卡里选，模型犯错最坏只是少合并。
2. **任务识别 **`temperature=0`：同一输入必须产出可复现标题；抓取、单聊、小群、@我 四路识别全部 `temperature=0`，合并也是。
3. **标题锚定（_stabilize_titles）**：重抓时把新标题向上一轮 pending 标题对齐（语义相似 + 共享专有名词）；同一天连抓两次标题集合完全一致。
4. **忽略记忆双层**：精确 `sig` 主路径 + 「同项目 + 相似度 + 共享专有名词」模糊兜底；容忍模型改写，不误杀同群里不同任务。
5. **四层回退链，且「降级」只指最后一层**：报告生成依次是 ① 流式 → ② 检出空正文（流式一个字都没回）→ ③ **加大输出额度**的一次性重试 → ④ 本地按项目罗列。中间换路只发 notice（告诉用户「换了条路」），**只有落到 ④ 才发 degraded**。把 notice 当降级信号，会让大模型实打实写出来的报告挂上「这篇不是大模型写的」，还把配好了 Key 的人指去查一个没问题的 Key —— 2026-09-22 线上就这么冤枉过一篇。
6. **重试必须换个打法**：空正文的成因是额度被模型的思考过程吃光，不是网络抖动 —— 用同样的额度再打一趟只会一模一样地再空一次，纯属浪费用户的等待时间。所以第二趟把额度翻倍（上限 32000），而不是原样重试。
7. **max_tokens 对推理型模型是「思考 + 正文」的总额度**，不是正文额度。一篇周报正文撑死 1500 token，思考却能轻松吃掉好几千：线上曾给 3600，结果 finish_reason=length、completion_tokens=3600、正文一个字都没有 —— 额度全花在思考上。现按「正文所需 × 数倍」给（周报月报 12000 / 实习总结 20000 / 简历条目 6000），超时同步放大（300 / 420 / 240 秒），因为思考阶段网关一个字节都不吐、额度越大这段静默越长。额度只是上限、按实际生成计费：**给大了不额外花钱，给小了轻则正文被截断、重则整篇空白。**
8. **前端永远不裸显示 markdown**：报告统一渲染成富文本；复制走 `text/html + text/plain` 双通道，粘到飞书 / Word 格式不丢。
9. **凭证不入代码**：`.env`、`llm keys`、`refresh_token` 只存服务端 SQLite / 环境变量；云端 `/root/凭证目录 为机主个人凭证，严禁外发。
10. **改稿失败绝不产出文本**（与生成路径相反的取舍）：生成失败会退回本地罗列 —— 「总要给用户一篇东西」；改稿不能这样，用户手上已经有一篇好稿，退回一篇罗列稿等于把它毁掉。所以改稿失败只发 error、编辑器一个字不动，且**绝不退回本地兜底**。改稿也**不落库、不碰 work_items**：报告本来就不落库，服务端全程无状态，成稿由前端带上来。
11. **改稿走「全文重写 + 逐行 diff 预览」，不做「查找串 → 替换串」补丁**：模型给的查找串经常和原文对不上（标点 / 全半角 / 空格），改不上还不报错。重写必然漂移，所以「采用」之前必须让用户看见逐行差异；diff 在 **markdown** 上算（即发给模型的那份），不在 HTML 上算。
12. **改稿素材按「生成时那个日期范围」快照取**：reportStart / reportEnd 是活的，用户生成完可能又去改日期。若改稿按新范围取素材，模型核对事实的依据就和这篇报告对不上 —— 会把原本正确的地方改错。生成时把范围快照下来，改稿带上它。
13. **状态档位按 kind 分，且白名单只有一份**：问题反馈与功能需求的档位不同（问题止于「已修复」，需求止于「已上线」），所以白名单是 {kind: (...)} 而不是一个扁平集合。校验下沉到 db 层 —— 改状态本来就要先查这一行，顺手就能拿到 kind。路由不再自己判一遍：两份白名单必然漂移，而漂移的表现是「某个 tab 改状态永远 400」。
14. **站内通知的已读标记是「最后一条别人回复的 id + 当时的状态」，不是时间戳**：消息时间是分钟粒度（now 截到分钟），同一分钟内「我看完 → 对方又回一条」会比不出先后、直接漏报。标记从裸回复 id 升级成 {r, s} 时，**老格式一律认成「不知道状态」** —— 否则上线瞬间，我参与过的每条帖子都会因为状态从空被补成「待处理」而集体报一次未读，一次误报就够让人不信这个红点。用户下次点铃铛写回新格式后自愈。
15. **下拉框的选中态必须绑在 option 上，不能写成 select 的 :value**：Alpine 按文档顺序初始化，select 上的 :value 会**先于**子级 x-for 求值，那一刻还没有任何 option，值对不上就退回显示第一项 —— 现象是「不管真实状态是什么，每张卡片都显示待处理」。绑 :selected 是在每个 option 建出来之后才求值，顺序天然正确。这类 bug **离线测试和 DOM 属性检查都看不出来**，只有截图能发现。

## 七、数据与隐私
- 每人只能看到、抓取、汇总**自己的**飞书消息（raw_messages / work_items 均带 owner_open_id）。
- 本地库 含各人 refresh_token 与大模型 key —— 敏感文件，仅存云端机，**不外传、不截图、不纳入版本控制（gitignore）**。
- 全部数据只留在个人云端机本地，不做任何外发；报告中的公司数据不离开内网。
- 内网文档（教程、本方案）读写一律走机主本地 `~/凭证目录 凭证 + feishu-sync，不走任何公开抓取通道。

## 八、部署与运维
- **形态**：云端机 Python venv + systemd（服务 `work-summary.service`），非 Docker；uvicorn 常驻 8002 端口。
- **自助部署**：机主在网页上传白名单内文件 → 服务端校验（`.py` 语法检查 + 路径白名单）→ 落盘备份 `.bak_时间戳` → `.py` 经 `systemd-run --on-active=2s` 平滑重启（~10-14s），`.html` 不重启、用户 Ctrl+F5 生效。响应回传落盘 md5，可核对一致性。
- **数据库**：单文件 本地库，定时不用管（个人工具量级）；取消/重启不丢已持久化数据。
- **改表结构只能靠启动迁移**：线上那台机器 SSH 不通、部署通道只能推文件、跑不了 SQL，所以 init_db() 里带了一批幂等启动迁移（建表 / 补列 / 回填老数据），每次启动跑一遍、补完即 0 行。新增字段优先走「读时兜底」，必须回填老数据时才加一段 —— 那是唯一够得着表的时机。
